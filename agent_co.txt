agent_co follow-up -- 2026-09-10 -- registers, speed and language quality
Ahmed asked: "What about prepare numbers for registers? How to make it
faster? How to make the language Qu better?"

Preparing execution before processing numbers is a useful direction.
There are two different meanings of registers here:
- Numbered variable slots: resolve names once, then operate on slots.
  Qu already does this for supported scalar loops and functions; see
  engine/crates/qu-interp/src/lib.rs:3634 (FastExpr/eval_fast), the
  whole-function fast path around 4021, and CompiledFn around 4550.
- Physical CPU/SIMD registers: compile a tight numeric kernel whose
  intermediate values can stay inside the processor. Qu's Vec<f64>
  slot array does not itself guarantee physical register allocation.
Ahmed has not yet specified which meaning he intended; both are covered.

IDEA: Prepare and fuse array expressions before evaluating their elements.
KIND: language
CASE FOR: For Y = A .* B + C, evaluate each output element in one loop:
load A[i], B[i], C[i]; multiply then add; store Y[i]. The product can stay
in a CPU register instead of a full temporary array. For three separate
same-shaped input arrays, separate multiply/add operations require six
logical element reads/writes (including the temporary); fusion requires
four. This removes one intermediate allocation. It does not establish a
speedup: caches, compilation cost, SIMD and workload size affect timing.
Qu's numeric kernels are already native; the opportunity is combining
operations. See benchmarks/README.md, Known gaps, and qu-core/src/matrix.rs.
CASE AGAINST: Fusion must preserve defined types, shapes, units, aliasing,
errors, function resolution and side effects. Restrict the first experiment
to pure, same-shaped numeric arrays with validated preconditions. Avoid
silently enabling floating-point reassociation or multiply-add contraction
that changes existing rounding. Tiny arrays may lose to preparation cost;
very large fused expressions can exhaust registers and spill to memory.
YOUR VERDICT: pursue
IF DROP, WHY: Not dropped; a bounded measured experiment, not a promise
of a particular speedup or authorization to change numerical semantics.
DEMONSTRATION GATE: Compare existing evaluation with a fused A .* B + C
implementation on small and large arrays. Measure result correctness,
total elapsed time, preparation time, repeat-call time and allocated bytes.
Include NaN/infinity/signed-zero and aliasing cases. Preserve operation
order under the existing numerical contract. Use Qu for auxiliary tooling;
engine kernels remain in the engine's implementation language. No new
benchmark or engine change was performed for this discussion.

IDEA: Reuse prepared plans and broaden the existing scalar register tier where profiles justify it.
KIND: language
CASE FOR: Cache reusable plans so repeated computation does not repeatedly
resolve names or rebuild expression trees. Extend the existing fast path
to frequently encountered unsupported expressions, rather than starting
another register subsystem. Current eval_fast still walks a typed tree;
a compact instruction sequence is a possible experiment if that traversal
is measured as costly. Existing whole-function caching is a starting point,
not a missing feature to reimplement.
CASE AGAINST: Cached plans become incorrect if function definitions,
relevant types/shapes, captures or other specialization assumptions change.
Require guards or invalidation for those assumptions. Do not cache input
values when only the execution plan is reusable. More compilation and
larger caches can hurt short-lived scripts, and scalar work may account
for little of an array-heavy workload's total time.
YOUR VERDICT: pursue
IF DROP, WHY: Not dropped, conditional on representative profiles showing
repeated preparation or unsupported scalar execution is material.
DEMONSTRATION GATE: Record cache hit/miss and preparation costs; compare
cold and repeated runs. Redefine a function or change an input type and
verify correct invalidation/fallback. Optimize time saved in actual work,
not the largest isolated slowdown ratio in a benchmark table.

IDEA: Apply SIMD to suitable fused kernels and explain optimization choices.
KIND: tooling
CASE FOR: After eliminating unnecessary array passes, SIMD can process
several elements per instruction. Expose preparation cost, selected path,
allocations and concrete fallback reasons so a user can understand why a
computation is slow. An unsupported operation should name the reason it
prevented optimization. This makes performance discoverable.
CASE AGAINST: Wider vectors do not fix excess memory traffic; register
pressure, CPU support, tails and small-array setup can erase gains. SIMD
reductions may alter floating-point order. LLVM documents these constraints
at https://llvm.org/docs/Vectorizers.html#reductions . Explanation output
must describe the actual chosen plan, not an independently maintained claim.
YOUR VERDICT: pursue
IF DROP, WHY: Not dropped; measure SIMD after establishing the fused baseline
and preserve numerical behavior. No ISA-specific speed claims were measured.
DEMONSTRATION GATE: Compare scalar and SIMD implementations over sizes,
unaligned inputs and tail lengths; confirm supported CPU selection and
fallback. Check explanation output against actual execution paths.

Language quality remains part of the recommendation: consistent flat and
method-call resolution, helpful signatures/shape information, and examples
that execute on the current engine. A concrete documentation inconsistency
found during this review is book/src/performance.md's obsolete description
of while-condition name collection: current try_fast_while_plan around
lib.rs:5605 already calls collect_fast_cond_names. Do not teach workarounds
for a limitation the current source has removed; refresh affected claims
with current measurements rather than copying historical timing ratios.

Suggested order: (1) bounded fusion experiment, (2) reuse preparation where
measured, (3) extend the scalar tier for demonstrated hot cases, (4) SIMD on
suitable kernels, (5) explain actual optimization decisions. Explanation can
be developed alongside each experiment. Historical benchmark notes identify
candidates but do not prove current end-to-end speedups.

This follow-up records recommendations only. No engine changes, performance
measurements, maturity promotions or publication were made. Existing hourly
checks remain responsible for new actionable file instructions; this saved
answer is not itself a request to launch every proposed experiment.

Ahmed's scope clarification -- 2026-09-10
"It's for signal processing, math computation and machine learning."

This clarifies the intended workloads; it does not choose between numbered
variable slots and physical CPU registers. Evaluate both against these
three application areas rather than treating scalar loops as the default.

Representative performance gates:
1. SIGNAL PROCESSING: an end-to-end window -> FFT -> spectral measurement
   pipeline, FIR/IIR filtering, and repeated processing of signal blocks.
   Measure throughput, per-block latency, allocations and numerical error.
   Profile repeated transform setup, reusable buffers and surrounding
   elementwise passes. Preserve state across blocks for streaming filters
   where the API calls for it; do not assume every filter is parallel across
   time samples. Hoist setup only when its inputs are unchanged.
2. MATHEMATICAL COMPUTATION: elementwise expressions, reductions, matrix
   multiplication, linear solves and repeated solves with an unchanged
   coefficient matrix. Test realistic dimensions and memory use. Consider
   reusable factorizations where applicable. Choose algorithms and remove
   temporary arrays before assuming wider SIMD is the main missing piece.
   Include small computations so setup costs cannot hide in large cases.
3. MACHINE LEARNING: representative training steps and repeated inference,
   including matrix operations, activations, reductions and gradient work
   when relevant. Measure full-step latency, throughput, peak memory and
   numerical agreement. Investigate per-element interpreter callbacks and
   repeated allocations. Fuse only supported pure operations with the
   correct forward and, where applicable, backward semantics. Explicitly
   define precision; no silent f64-to-f32 change to obtain a faster number.

An appropriate direction is a shared prepared numeric representation that
can describe typed scalar operations, array operations, shapes, units where
present, and side effects. It should enable guarded reuse, pure elementwise
fusion and calls to existing specialized kernels. FFTs, factorizations and
matrix products should retain suitable specialized algorithms; they do not
all become one generic elementwise loop. Preserve each operation's defined
semantics and use physical registers for short-lived values where generated
code permits. Do not attempt to fit entire scientific arrays into registers.

The previous priority ordering is provisional. Weight measured time saved
by Ahmed's actual workload mix: a streaming filter, a large matrix solve
and an ML training step can have different bottlenecks. Report per-domain
results and complete pipelines, with cold versus repeated execution shown
separately. Do not extrapolate a single fusion benchmark to all of Qu.

Language-quality goal: users should be able to express these workloads
clearly, inspect shape/type/unit and precision behavior, understand errors,
and reproduce results. Automatic optimization should reduce the need for
manual performance tricks while preserving the same computation.

Recorded clarification and evaluation criteria only; no implementation,
new measurement or maturity promotion is claimed.
