resize

Builtin index · Images

result = resize(img, width, height, [method="nearest"])

Input: img, width, height, method · Output: result

What it is

img is an Image; width/height are positive integers giving the absolute target size in pixels (not a scale factor — see imscale for that). method is an optional named string: "nearest" (default, cheap nearest-neighbor) or "bilinear" (smoother).

Overloads

img can be Image or Vec; method can be string or Vec.

Ask an image its dimensions with .width and .height, not with a tuple. Every call in this chapter that takes a size takes it as width then height — image_new(width, height), resize(img, width, height), crop(img, x0, y0, width, height) — and a named accessor cannot be read in the wrong order the way a pair can. img.width means the same thing however the language chooses to order a returned pair, so code written against it does not depend on remembering a convention, and does not change meaning if that convention is ever revisited.

For completeness: size(img) returns [width, height] — the same order every call above takes — and length(img) returns the pixel count, which has no order to get wrong. There is no worked example of size on an image on this page yet, deliberately: the build that renders these pages runs an engine older than that behaviour, so an example printing it would show you a number the current engine does not produce, over the build's signature. It will be added once the two agree.

Examples

Written for this form and run by the build -- the output below is what the engine actually produced.

v = [1, 2, 3]
print(resize(v, 5, fill=9))   # [1, 2, 3, 9, 9] -- grown, padded with 9

print(resize(v, 2))           # [1, 2]          -- shrunk, tail dropped
output
[1, 2, 3, 9, 9]
[1, 2]

How it works

resize(img, width, height, [method="nearest"|"bilinear"]) — nearest-neighbor by default (matches most languages' cheap first-pass resize); method="bilinear" for smoother scaling. resize(vec, new_length, [fill=0.0]) — overloaded on argument type, not a separate name (same pattern as zeros(filt) above): BASIC's ReDim Preserve, offered as an explicit, visible call rather than an implicit side effect of assignment (see the out-of-bounds index-assignment decision silent-bug risk, a typo'd index would silently resize instead of erroring, but a deliberate, named resize(...) call carries none of that ambiguity: the intent to grow/shrink is right there in the source). Returns a NEW vector of exactly new_length, same immutable-return convention as append/hstack/vstack: growing keeps every existing value in its original position and pads the new trailing slots with fill; shrinking truncates (keeps the first new_length elements, matching ReDim Preserve's own shrink behavior — dropping the tail, not an error).
