particle_filter

Builtin index · Statistics & ML

result = particle_filter(n_particles, initial_state, [process_noise=0.05], [obs_noise=1.0], [spread=1.0], [seed=])

Input: n_particles, initial_state, process_noise, obs_noise, spread, seed · Output: result

What it is

The specialized constant-velocity tracker: n_particles (integer), initial_state (a length-D position/velocity vector), process_noise/obs_noise (numbers, the built-in noise levels — no Q/R argument needed at predict/update time), spread (number, initial scatter), and an optional integer seed=.

Overloads

One call shape — this function is not overloaded.

How it works

particle_filter(n_particles, initial_state, [process_noise=], [obs_noise=], [spread=1.0], [seed=]) — a SEPARATE, more specialized filter than particle_filter_init just above: that one is fully generic (arbitrary user-defined transition/ likelihood functions, any state layout); this one hardcodes a constant-velocity position/velocity motion model specifically so its predict step is a single matrix multiply — n independent, identical per-particle updates — and can therefore be GPU-dispatched (see particle_tracker_advance's own doc comment for the real, measured GPU-vs-CPU crossover). initial_state must have an EVEN length d = 2*half: the first half entries are position components, the last half are the matching velocity components (e.g. [x, vx] for 1-D tracking, [x, y, vx, vy] for 2-D). Model kind "particle_tracker" — kept distinct from the generic filter's "particle_filter" kind so this filter's own .predict(dt)/.move(dt)/.update(observation)/ .estimate() contract (fixed motion/observation models, no function names) never collides with the generic filter's function-name-based one above. process_noise/obs_noise are stored ON the returned model (unlike the generic filter, which takes Q/R fresh on every call) so .predict(dt)/ .update(z) need only the time-varying argument.
