multi_head_attention

Builtin index · Statistics & ML

result = multi_head_attention(x, heads, n_heads)

Input: x, heads, n_heads · Output: result

What it is

Runs several attention heads over the same (N, D) input x in parallel: heads is a tuple of n_heads (integer) Records, each with fields wq, wk, wv (per-head projection matrices) and wo (the head's output projection), and self-attention (q = k = v = x projected through each head's own weights) is computed per head, then the results are combined through each head's wo and summed.

Overloads

One call shape — this function is not overloaded.

How it works

multi_head_attention(x, weights, n_heads, [mask]) — splits into n_heads independent heads, each with its own wq/ wk/wv/wo projections, and combines them. weights is a Value::List of exactly n_heads Value::Records, each {wq, wk, wv, wo}: wq/wk/wv are (d_model, d_head) (x @ wq projects x's (seq_len, d_model) down to this head's own (seq_len, d_head) q/k/v), and wo is (d_head, d_model) — this head's own ROW-BLOCK slice of the usual combined output projection. Concatenating the heads' (seq_len, d_head) outputs and multiplying by one big (n_heads*d_head, d_model) Wo is the textbook formulation, but it needs a concat tracked primitive nothing else here needs (TapeEntry only carries two input slots, so a variadic concat was never on the table anyway). Splitting Wo into per-head row blocks (wo above) and SUMMING attn_head @ wo_head instead is the identical computation by the standard block-matmul identity ([A1 A2] @ [B1; B2] == A1@B1 + A2@B2) — so this needs only tb's existing "*"/"+", no new primitive and no new tensor_vjp rule. CPU parallelism: heads run in a sequential Rust for loop, not a rayon fan-out, because every iteration mutates self.tape (&mut self) — racing multiple heads across threads against one shared, non-atomic Vec<TapeEntry> would corrupt node numbering, the same constraint gru_forward's own doc comment documents for timesteps. The actual parallel win is one level down: each head's own Q@K^T/probs@V matmuls already run on qu-core's rayon thread pool once they cross Matrix::PARALLEL_MATMUL_THRESHOLD, same as every other tracked matmul in this interpreter.
