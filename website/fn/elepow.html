elepow

Builtin index · Core maths

result = elemul(a, b, ...)

Input: a, b, ... · Output: result

What it is

The .*, ./ and .^ family: always elementwise, whatever the shapes. The distinction from mul/div/pow only bites on matrices, which is exactly why both families have names.

Overloads

One call shape — this function is not overloaded.

How it works

zip/map/dict (§47.4, scoped/shipped 2026-08-26 — see BACKLOG.md "for over collections, zip, map, dict") (see that module's own doc comment); these arms are just the thin wiring into it. get/set/keys/values are plain functions, not new syntax — d.get("k") already works for free via eval_call's existing recv.method(args) == method(recv, args) sugar. The operators as named functions, for the places a NAME is what you can pass: reduce-style folds, a table of operations, a pipeline stage. Each one routes through the very same binop the operator does, so there is no second set of arithmetic rules that could drift from the first -- broadcasting, units, complex, matrices and every error message are whatever a + b already does. mul/div follow * and /, which on two MATRICES mean matrix multiply and solve. elemul/elediv are .* and ./ -- always elementwise, whatever the shapes. That is the one distinction worth having names for, and the reason both families exist rather than just the short ones. Variadic and folded left, so add(a, b, c) reads as the sum it looks like rather than needing to be nested. subtract, not sub: sub is a KEYWORD -- it opens a subroutine -- so a builtin of that name could never be called. The parser rejects sub(a, b) before the interpreter is reached.
