  Unit handling: scalar rejects what vector accepts
    CONFIRMED 2026-09-11 against the master-vintage binary
    (relocated-session, HEAD 3cca8198, 0 ahead/0 behind; date any
    binary with `qu eval "tic(1)"` -- it must suggest help("tic"), not
    available("tic")). CORRECTED after agent_co (Codex) caught an error
    in the first version of this row: I had written that abs STRIPS the
    unit from a vector. It does NOT -- the tag survives. Verified:
    print("{abs([1 ohm, -2.5 kohm])}") => [1, 2500] Ohm. My original
    probe used print(...) and saw [1, 2500], which is a DIFFERENT
    defect, recorded separately below. The real inconsistency is
    scalar-vs-shape-vs-arity: abs(9 ohm) errors "cannot apply the
    operation to unit" while abs on a unit VECTOR works and keeps the
    tag; sin(9 ohm)=>0.412118, exp(1 ohm)=>2.718282, log(9
    ohm)=>2.197225, sqrt(9 ohm)=>3 all unwrap the same scalar; max(9
    ohm)/min(9 ohm)/mean(9 ohm) error "expected a numeric vector, found
    unit" while max([9 ohm])=>9, sum([9 ohm])=>9, max(9 ohm, 10
    ohm)=>10 succeed. Note abs is stricter in the one case where
    strictness is LEAST justified: abs of a resistance is a resistance,
    sin of a resistance is dimensionally meaningless and currently
    succeeds. Silent scalar unwrapping is documented
    (docs/design/physical-units.md phase 2); this inconsistency is not.
    Ahmed to choose the rule -- precedent is his "1 V == 1 is no"
    ruling.

  print(v) and "{v}" disagree on unit vectors
    FOUND 2026-09-11 while checking Codex's correction; this is what
    made me misreport the row above. Two render paths give different
    answers for the SAME value. Scalars agree: print(1 ohm) => 1 Ohm
    and print("{1 ohm}") => 1 Ohm. Vectors do not: print([1 ohm, 2
    ohm]) => [1, 2] but print("{[1 ohm, 2 ohm]}") => [1, 2] Ohm. Not
    specific to ohms or to abs -- print([1 s, 2 s]) => [1, 2] versus
    "{...}" => [1, 2] s. So print() silently drops the unit for vectors
    while keeping it for scalars, and string interpolation keeps it for
    both. The consequence is worse than cosmetic: it makes unit loss
    LOOK like it happened when it did not, which is exactly how the row
    above got written wrong.

  zeros/ones silently drop dimensions beyond the second
    FOUND by agent_co (Codex) P04/P10, CONFIRMED 2026-09-11 on the
    master-vintage binary. size(zeros(2,3,4)) => [2, 3];
    size(zeros([2,3,4])) => [2, 3]; size(ones(2,3,4)) => [2, 3]. The
    third dimension is discarded in silence -- no error, no warning, a
    plausible-looking wrong shape. Fractional sizes are also accepted:
    size(zeros(2.5,3)) => [2, 3]. Codex traces it to shape_args marking
    ALL arguments read while consuming only two, which is why the
    kwarg/arity validation added recently does not catch it. Codex also
    reports higher-dimensional MAT imports flatten dimensions
    (source-only, not run here). This is the silent-wrong-answer class,
    not a missing feature: rejecting invalid rank and fractional sizes
    is a small fix and must not wait for a general N-D redesign.

  plot() silently discards a string y-series and plots the row index
    FOUND by agent_q, CONFIRMED 2026-09-11 on the master-vintage
    binary. plot([1,2,3], ["a","b","c"]) SUCCEEDS -- "plot: figure 1 (3
    points)" -- and plots the row index 0..n-1 as y, discarding the

    5c151fcf75a98aafd065c9871c379c62, 8110 bytes each). The reader sees

    Documented contract is numbers -- book/src/stdlib/plotting.md line
