# CSV load + multi-filter benchmark

A real analysis workflow rather than a synthetic kernel: generate a signal,
write it to CSV, then measure (a) reading that CSV back from disk and
(b) applying five different filters to the loaded column. `bench.qu` and
`bench.py` build the *same* dataset (same seed, same formula) and run the
*same* five filters, so the numbers are directly comparable.

Run:

```bash
qu run benchmarks/csv_filters/bench.qu
python benchmarks/csv_filters/bench.py
```

## Dataset

500,000 samples at `Fs = 10 kHz` (50 s of data), three tones (50 Hz, 500 Hz,
2000 Hz) plus Gaussian noise — `signal.csv` is ~8 MB, regenerated by each
script's own run (gitignored, not committed — deterministic from the seed,
so nothing is lost by not tracking it).

## Filters

| Filter | Qu | Python |
|---|---|---|
| Butterworth lowpass (order 4, 200 Hz), causal | `sosfilt(butter(4,"low",200,Fs), x)` | `sosfilt(butter(4,200,btype="low",fs=Fs,output="sos"), x)` |
| Butterworth highpass (order 4, 1000 Hz), causal | `sosfilt(butter(4,"high",1000,Fs), x)` | same, `btype="high"` |
| Butterworth bandpass (order 4, 300–800 Hz), causal | `sosfilt(butter(4,"band",[300,800],Fs), x)` | same, `btype="band"` |
| Butterworth lowpass, zero-phase | `filtfilt(lp, x)` | `sosfiltfilt(lp, x)` |
| FIR moving average (51-tap), same-length | `conv(x, ones(51,1)/51, mode="same")` | `np.convolve(x, ones(51)/51, mode="same")` |

The lowpass's job is to isolate the 50 Hz tone: `rms(y_lp)` should land near
`1/sqrt(2) ≈ 0.7071` (correct in both — 0.7077 Qu, 0.7072 Python, matching
to 3 decimals, cross-checking the filter design/application itself, not
just the timing).

## Results (this machine, single trials — not statistically rigorous)

| Step | Qu | Python (pandas + scipy) |
|---|---|---|
| `csv_load` (500k rows) | 0.038–0.044 s | 0.048–0.078 s |
| `butter_lowpass` | 0.003 s | 0.003 s |
| `butter_highpass` | 0.003 s | 0.002 s |
| `butter_bandpass` | 0.004 s | 0.003 s |
| `butter_filtfilt` | 0.007–0.008 s | 0.007 s |
| `moving_average_fir` | 0.006–0.008 s | 0.005–0.006 s |
| **total** | **0.06–0.07 s** | **0.07–0.10 s** |

**Honest read**: the four `sosfilt`/`filtfilt` filter steps are essentially
tied — both call into a tight biquad-cascade loop, and Qu matches scipy's
compiled C here. `csv_load` originally trailed pandas by ~2–3x (0.13–0.16s
vs 0.05–0.08s) — see "`read_csv` acceleration" below, now fixed: Qu edges
out pandas on this file.

Ahmed also pointed at [polars](https://pola.rs) (itself Rust) as a sharper
target than pandas. Measured on this same file: **0.16–0.18s cold** (first
call pays thread-pool spin-up) but **0.004s warm** — roughly 10x faster
than Qu's own number even after the fix below, all from one process
reading the same file repeatedly. That gap is architectural, not a small
tweak: polars memory-maps the file, parses in parallel across row-group
chunks with SIMD-accelerated float parsing, and its numbers here are a
warm-process, repeated-call figure — not shown as "the" comparison above
since `read_csv`'s single-call, cold-file numbers are what an actual Qu
script pays. Worth keeping as the honest long-term target if `read_csv`
performance matters more later: parallel chunked parsing is a real,
scoped project (split the file on row boundaries, parse chunks on separate
threads via the existing `rayon` dependency, concatenate columns) — not
attempted this pass.

### `read_csv` acceleration (this session)

`Table::from_csv` (`engine/crates/qu-interp/src/table.rs`) originally
buffered every CSV cell as an owned `String` in a `Vec<Vec<String>>`, then
ran a *second* pass parsing each string to `f64` — for this 500k-row,
2-column file that's a million throwaway heap allocations before any
actual parsing happens. Rewritten to a single pass that parses each
numeric field directly from its borrowed `&str` slice into a pre-sized
`Vec<f64>` (row count estimated up front from a newline count, so the
`Vec` isn't repeatedly doubled either); a column only ever allocates
`String`s if it's genuinely text, or falls back retroactively if a
numeric column hits an unparseable cell partway through (converts what's
been collected so far, then continues as text — same all-or-nothing
per-column typing as before, just computed lazily instead of in two
passes). **Result: 0.13–0.16s → 0.038–0.044s, ~3.6x**, all existing CSV
round-trip tests (numeric, text-fallback, file round-trip) still pass.

`Table::to_csv` (the write side) had the same shape of waste — a
`Vec<String>` + `.join(",")` allocated fresh per row — fixed the same way
(write fields straight into one pre-sized buffer). Checked against pandas'
own `to_csv` on the same 500k-row file: **Qu 0.56s vs pandas 0.88s** — Qu
was already ahead here even before the fix (float-to-string formatting,
not container overhead, dominates CSV writing in both languages), so this
was a smaller, lower-priority win than the read side, not a gap that
needed closing.

## Tests

No dedicated `#[ignore]`d test for this one (it's a same-language-pair
timing comparison, not an algorithm-correctness check like the private
crest-factor scripts) — the `rms(y_lp)` sanity print in both scripts is the
"did the filters actually do the right thing" check, confirmed matching
above.
