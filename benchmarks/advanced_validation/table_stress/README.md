# Table stress test: `group_by_agg` / `corrcoef` / filter+sort vs pandas

Goes well beyond `../../data_wrangling/bench.qu`: that script exercises the
same table builtins at larger scale (1M rows) but is **self-timed only** —
it prints its own numbers and never diffs them against pandas/MATLAB, so it
can't catch a correctness bug (its own doc comments say as much). This
scenario takes the opposite priority — a realistic but modest 30,000-row
table, and every result cross-checked against pandas/numpy ELEMENTWISE
(the `../ml_stress/` "dump Qu's own output to CSV, diff it in Python"
discipline), not just eyeballed:

1. **`group_by_agg`** — mean/sum/count of a value column, grouped by a
   15-category text column, vs pandas `.groupby().agg()`.
2. **`corrcoef`** — full 4x4 pairwise Pearson correlation matrix of the
   numeric columns, vs `pandas.DataFrame.corr()` (cross-checked against
   `numpy.corrcoef` too, as a sanity check that those two agree with each
   other before either is trusted as ground truth).
3. **A filter+sort chain** — `df[df.price > x].sort_values("sortkey")`, vs
   the identical `filter(...)`/`sort_by(...)` chain in Qu.

Run:

```bash
python benchmarks/advanced_validation/table_stress/make_data.py   # once, regenerates dataset.csv
qu run benchmarks/advanced_validation/table_stress/table_stress.qu # also dumps 3 result CSVs
python benchmarks/advanced_validation/table_stress/table_stress.py # diffs them elementwise
```

## Dataset

`make_data.py`: 30,000 rows, seeded (`np.random.default_rng(42)`), one
categorical grouping column (`region`, 15 groups `R00`..`R14`, unevenly
weighted via a fixed Dirichlet draw — real region/store tables are never
perfectly balanced) and four numeric columns with real linear correlation
structure built in, not independent noise:

- `price` — `Uniform(5, 500)`
- `qty` — integers `[1, 50)`
- `amount = 0.6*price + 2.0*qty + N(0, 20)` — strongly correlated with
  `price`, moderately with `qty`
- `score = 0.05*price + 0.3*qty + N(0, 15) + 50` — weakly correlated with
  both (smaller coefficients, more noise) — deliberately included so
  `corrcoef` has a mix of strong/weak/near-zero correlations to get right,
  not just one obviously-correlated pair
- `sortkey` — independent `Uniform(0, 1000)`, tie-free at double precision
  across 30k draws, used only for the filter+sort chain so row order is
  unambiguous

Both `table_stress.qu` and `table_stress.py` read the identical
`dataset.csv` — no per-language regeneration. `dataset.csv` is ~2.4MB, over
this repo's usual "keep it committed" threshold, so it's `.gitignore`d
(same precedent as `peak_finding/`'s noise CSVs) and regenerated by
`make_data.py`; the three small Qu-output CSVs it produces
(`group_agg_qu.csv`, `corrcoef_qu.csv`, `filter_sort_qu.csv`, all under
1MB combined) stay committed.

## Two API workarounds needed (documented in `table_stress.qu`'s header)

`df.region` (a text column) has no Qu value type of its own yet — no
vector-of-strings type, so its values can't be iterated or printed from
inside a Qu script (same limitation `../../data_wrangling/bench.qu`'s own
comments describe). Two different ways around it were needed here:

- **`group_by_agg`'s result** (one row per group, small) is put in a fixed,
  language-independent order with `sort_by(g, "region")` — alphabetical by
  the group-label column, matching pandas' own `.groupby().sort_index()`
  order — then the aggregate columns are compared positionally.
- **The filter+sort result** (15,232 rows, too many to iterate/print
  row-by-row from Qu anyway) is written straight out with `write_csv`,
  which serializes every column — including `region` — directly from Rust.
  Only *printing from inside a Qu script* is restricted; `write_csv` isn't.

`corrcoef(X)` also needs a plain numeric `Mat`, not a `Table` — there's no
`to_matrix(table)` builtin, so `X` is built explicitly with
`hstack(df.price -> (n, 1), df.qty -> (n, 1), df.amount -> (n, 1), df.score -> (n, 1))`
(the `->` reshape operator, sugar for `reshape(col, n, 1)` — see
"ergonomic API layer" below), the same pattern `../ml_stress/ml_stress.qu`
uses for its feature matrix.

## Ergonomic API layer (2026-08-31, syntax facelift only)

`table_stress.qu` was rewritten to use the newer ergonomic aliases —
`table.load`/`table.write` for `read_csv`/`write_csv`, `df.nrows`/`df.ncols`
property access for `nrow(df)`/`ncol(df)`, `timer.start()`/`timer.stop()`
for `tic()`/`toc()`, and `col -> (r, c)` for `reshape(col, r, c)`. Every one
of these is pure sugar for the exact same underlying builtin — re-run
against a fresh release build and re-diffed byte-for-byte against the
CSVs already committed here (`group_agg_qu.csv`, `corrcoef_qu.csv`,
`filter_sort_qu.csv`): identical output, identical accuracy, no behavior
change, only the spelling.

## Results — speed

Single-trial timings, same machine, same "not statistically rigorous, good
enough to see the shape" caveat as the rest of this benchmark suite. Five
repeated trials were run for each op to gauge noise at this small a scale
(the whole 30k-row workload finishes in tens of milliseconds on both
sides, so run-to-run jitter is a bigger fraction of the number than in the
suite's other, longer-running scenarios); the table below reports one
representative trial, with the observed range noted in prose.

**BEFORE (original finding, kept for the record):**

| operation | Qu | pandas/numpy | ratio |
|---|---:|---:|---:|
| load / read_csv | 10.6 ms | (not separately timed by pandas `read_csv` above) | — |
| `group_by_agg` / `.groupby().agg()` | 5.1 ms | 5.2 ms | **~1.0x (parity)** |
| `corrcoef` / `.corr()` | 21-24 ms | 1.5-2.4 ms | **Qu ~10x slower** |
| filter + sort | 6.5 ms | 1.6-1.9 ms | **Qu ~3.6x slower** |

Across 5 repeated trials each: Qu's `group_by_agg` ranged 4.6-7.2 ms
against pandas' 3.6-6.0 ms (essentially a tie, sometimes Qu edges ahead);
Qu's `corrcoef` ranged 19-24 ms against pandas'/numpy's 1.5-3.7 ms (a
consistent, real ~8-13x gap, not noise); Qu's filter+sort ranged 5.7-8.1 ms
against pandas' 1.6-3.1 ms (a consistent ~3-4x gap).

**AFTER (2026-08-31 fix — see "What was actually wrong" below), same
machine, same 5-trial protocol, fresh release build:**

| operation | Qu (before → after) | pandas/numpy | ratio (before → after) |
|---|---:|---:|---:|
| `group_by_agg` / `.groupby().agg()` | 5.1 ms → 2.3-3.9 ms | 5.2 ms | ~1.0x → **Qu often faster** |
| `corrcoef` / `.corr()` | 21-24 ms → 1.2-1.9 ms | 1.5-2.4 ms | ~10x slower → **~1.0x (parity, sometimes faster)** |
| filter + sort | 5.7-8.1 ms → 2.0-2.7 ms | 1.6-1.9 ms | ~3.6x slower → **~1.2-1.4x slower** |

Cross-checked against a fresh `table_stress.py` run on the same rebuilt
CSVs: `corrcoef` 1.2-1.9 ms vs. pandas' `.corr()` 1.6 ms and numpy's
agreeing to 2.6e-15; filter+sort 2.0-2.7 ms vs. pandas' 1.6 ms. `corrcoef`
went from the worst gap in the suite (~10x) to indistinguishable from
pandas at this scale — some trials Qu is faster, some pandas is, both
within single-digit milliseconds of each other. filter+sort closed from
~3.6x to ~1.2-1.4x — most of the gap, not all of it.

## What was actually wrong (not "BLAS is just better")

Both gaps turned out to be real, fixable Rust-side overhead, not an
inherent BLAS-vs-young-table-engine ceiling — confirmed by reading the
actual hot paths rather than assuming:

1. **`corrcoef`'s own math (`corrcoef_matrix` in `qu-interp/src/lib.rs`)
   was already correct and efficient** — column means/centered
   values/norms are computed once per column up front, not recomputed
   per pair, and the O(N²) part is already halved via symmetry. The
   9-13x gap was NOT in the correlation math at all. It was upstream, in
   building the input matrix: `table_stress.qu` (like any realistic
   script with no `to_matrix(table)` builtin) builds `X` via
   `hstack(reshape(df.price, n, 1), reshape(df.qty, n, 1), ...)` — several
   `Nx1` column matrices concatenated side by side. The shared
   `hstack`/`vstack`/`cat`/`[a, b]` block-concatenation code
   (`value_to_block`/`hconcat_blocks`/`vconcat_blocks`/`block_to_value`)
   stored its intermediate `Block` as `Vec<Vec<f64>>` — row-major, one
   heap-allocated `Vec` per row. For a tall `Nx1` matrix (N=30,000) that
   meant 30,000 individual single-element-`Vec` allocations just to read
   the matrix in (`Matrix::row_vec` per row), then another 30,000-row
   gather/transpose (`Matrix::from_rows`) to assemble the result — for
   *every one* of the 4 columns being stacked. Fixed by rewriting `Block`
   to store column-major (matching `Matrix`'s own layout): a `Value::Mat`
   converts via one `to_vec()` of its already-column-major buffer,
   `hconcat_blocks` (equal row counts) becomes a straight buffer
   concatenation, `vconcat_blocks` (equal col counts) copies one
   contiguous per-block-per-column slice at a time, and `block_to_value`
   hands the buffer straight to `Matrix::from_col_major` with no
   transpose. Zero allocations-per-row instead of tens of thousands.

2. **`Value::Table` was the one compound value type never `Arc`-wrapped.**
   `Value::Vec`, `Value::Mat`, `Value::CVec`, `Value::CMat`, and
   `Value::Signal` had all already been switched to `Arc<...>` in an
   earlier perf pass specifically so a variable *read* is an O(1) refcount
   bump instead of an O(n) deep clone — `Value::Table(Table)` was left
   behind as a bare, un-`Arc`'d value. Every reference to a table
   variable (`Expr::Name`'s `var_get(n).cloned()`, and every function-call
   argument evaluation) deep-cloned the *entire* table: every numeric
   column's `Vec<f64>` (a memcpy) AND every text column's `Vec<String>`
   (one heap allocation *per string*, not just a memcpy). A single run of
   `table_stress.qu` references `df` roughly ten times (`nrow(df)`,
   `ncol(df)`, `group_by_agg(df, ...)`, four `df.col` reads building the
   `corrcoef` matrix, then `filter(df, df.price > ...)`'s own two
   references) — each one a full 30,000-row, 5-column table clone
   (including a fresh clone of the 30,000-entry `region` text column)
   before the read it was actually there for even happened. Fixed by
   changing `Table(Table)` to `Table(Arc<Table>)`, the exact same
   copy-on-write convention already used everywhere else — safe by
   construction here since every `Table` method already takes `&self` and
   returns a new `Table` (confirmed: zero `&mut self` methods anywhere in
   `table.rs`), so there is no in-place-mutation path that Arc-sharing
   could make two aliases interfere through.

Both fixes are pure performance changes — same algorithms, same floating-
point results, same row order, verified via a fresh `table_stress.py`
elementwise diff (still 0 mismatches, see below) plus new unit tests
(`hstack_of_tall_skinny_column_matrices_matches_manual_construction`,
`corrcoef_of_hstacked_reshaped_columns_matches_hand_built_matrix`,
`table_arc_sharing_does_not_let_one_alias_mutate_another`, and others in
`qu-interp/src/lib.rs`'s test module) plus the full `cargo test --workspace`
suite (992 passed / 1 pre-existing, confirmed-flaky, unrelated worker-pool
scheduling test that passes on its own — nothing in `Block`/`Table`/
`corrcoef`/`filter`/`sort_by`).

**What's left, and why it's genuinely architectural now:** filter+sort's
remaining ~1.2-1.4x gap (down from ~3.6x) is what's left after removing the
two overhead sources above — the actual per-element work (`Column::take`'s
bounds-checked indexed gather for the filter, `Vec::sort_by`'s comparison
sort for the sort) is now the dominant cost, and closing the rest would
mean either unsafe unchecked indexing or switching away from a stable sort
(`sort_by` currently preserves tie order, matching a documented, tested
contract — `vstack_rejects_two_plain_vecs_of_different_length` and friends
don't test this directly, but nothing in the test suite currently allows
tie order to change, so this wasn't touched). That's a real but much
smaller remaining gap than the original investigation found, not "BLAS is
just better" — most of what looked architectural was actually two
concrete, fixable inefficiencies once the code was actually read.

## Honest verdict

**Correctness: still no bugs found, before or after.** All three
operations — `group_by_agg`, `corrcoef`, and a filter+sort chain — match
pandas/numpy exactly (to `write_csv`'s inherent 6-decimal-place CSV
rounding, not a computation difference) across every group, every matrix
entry, and every one of 15,232 filtered+sorted rows, on both the original
and the fixed build. This is the same "elementwise diff, not just
eyeballed numbers" standard as `../ml_stress/`, and it comes back clean
both times.

**Speed: the original ~8-13x and ~3-4x gaps were mostly NOT an inherent
BLAS/library-tuning ceiling.** They were dominated by two concrete,
fixable Rust-side inefficiencies (a row-major intermediate in matrix
block-concatenation, and a missing `Arc` wrapper on `Value::Table`) that
had nothing to do with the correlation or sorting algorithms themselves.
Fixing both brought `corrcoef` to parity with pandas/numpy and closed most
(not all) of the filter+sort gap. The residual ~1.2-1.4x on filter+sort is
the more honest candidate for "this is what raw per-element overhead looks
like at this scale" — but even that is far smaller than the ~3.6x
originally reported, and came from removing real overhead first rather
than assuming a library-tuning ceiling and stopping there.
