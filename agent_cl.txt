You are being asked to attack the ladder itself, not to use it.

agent_q is testing functions. agent_co is generating ideas. Your job is
the one neither of them can do: decide whether the machinery that
classifies 838 functions is measuring what it claims to measure.

WHAT THE MACHINERY DOES

tools/gen_version_ladder.qu scrapes BUILTIN_NAMES from the interpreter,
then counts CALL SITES for each name across five corpora:

  docs      book/src/stdlib/*.md  (minus builtin-index.md, which lists
                                   every name and would make the whole
                                   language look documented)
  tests     engine/crates/*/tests/*.rs PLUS the #[cfg(test)] region of
            qu-interp/src/lib.rs, which is where most tests actually are
  bench     benchmarks/**
  examples  catalog/**, example_codes/**
  private   private/**   (an RC gate: no private leak)

From those counts it assigns:
  >=1 test and >0 bench  ->  0.1.0-4.aplus  (Alpha++)
  >=1 test               ->  0.1.0-3.a      (Alpha)
  otherwise              ->  0.1.0-2.x      (Next)

and it stops there. Beta, RC and Public require a signed row from Ahmed
in versions/ladder.tsv. A signature the evidence contradicts -- Beta
with zero tests, Public while private/ names the function -- is printed
as a contradiction rather than believed.

The project version is the LOWEST rung any function sits on. Today:
Next 191, Alpha 491, Alpha++ 156, and so the project computes to
0.1.0-2.x.

WHERE I ALREADY THINK IT IS WEAK -- go further than this

  1. A CALL SITE IS NOT A TEST. `zeros` appears 63 times in the test
     corpus, but almost certainly as SETUP for testing something else,
     not as the subject. The count cannot tell the difference between
     "63 tests of zeros" and "63 tests that happened to need a zero
     vector". This is the single biggest lie in the current model and I
     do not have a fix for it. Do you?

  2. A BENCHMARK IS NOT A COMPARISON. Alpha++'s stated gate is "on par
     with MATLAB and/or Python and/or Matty". What the tool actually
     checks is that the name appears somewhere under benchmarks/. It
     does not check that a number was produced, that a comparison was
     made, or that Qu won. 156 functions currently sit at Alpha++ on
     that basis. How many deserve it?

  3. DOCUMENTED IS TWO DIFFERENT QUESTIONS. The tool counts a name as
     documented if a chapter calls it OR backticks it. A name mentioned
     in passing in someone else's example scores the same as a name with
     its own table row.

  4. THE PRIVATE GATE MAY BE BACKWARDS. 37 names appear in private/ --
     including `sin`, `mean`, `plot`, `sum`. Those are not leaks; they
     are ordinary functions used by private code. Flagging them at the
     Public gate would block the entire language. The gate probably
     needs to ask something else entirely, and I do not know what.

  5. NOTHING ENFORCES ANY OF IT. There is no test that fails when a new
     builtin lands with no rung. It was argued that there should be.
     Ahmed has not been asked yet whether the gates should have teeth --
     that is his decision, not mine and not yours.

WHAT WOULD BE USEFUL

Tell me which of the five above is worst, and whether any of them makes
the whole exercise misleading rather than merely imperfect. If the
honest answer is "this model dresses up a name-frequency count as a

Then, if you can: propose ONE change that removes the most falseness for

I did not argue from the tool's comments. I ran its tokenizer on the
release qu.exe and re-counted its corpora with grep. Every number below
has the command that produced it, so re-run rather than trust.

WEAKNESS: A new one you missed, plus your #2. The COUNTER itself has
  three blind spots, and they move real rows:

  (a) Escaped newlines. Tests embed Qu programs in Rust strings, so a
      call at the start of a line looks like `\nplot(`. IDENT lacks the
      backslash, so trailing_ident() walks back over `nplot` and stops at
      `\` -- the token counted is `nplot`, which matches nothing. On the
      real binary: trailing_ident("x = 1\nplot") -> "nplot". Verified.
      235 calls across 72 builtins vanish this way (plot 78, print 39,
      xlabel 9, title 8). 28 functions sit at Next ONLY because of this:
      heatmap, imagesc, spectrogram, stackbar, semilogx, semilogy,
      xticks, xticklabels, ylim, nyquist, violin, hexbin, ecdf, eda ...
  (b) Method syntax. IDENT includes `.`, deliberately, to drop Rust's
      `.len(` and `.sum(`. But Qu's own OOP sugar routes to the same
      dispatch table, and tests written the idiomatic way are invisible:
      `lp.pzplot()`, `lp.fvtool(64)`, `x.diff()`, `q.push(v)`.
      trailing_ident("lp.pzplot") -> "lp.pzplot". 36 Next-rung names
      have method-syntax test calls and zero counted: push 78,
      is_empty 39, count 35, update 23, pop 10, freqz 8, pzplot 4,
      fvtool 4, matmul 3 (some of those are Rust host calls, most are Qu).
  (c) Rust host calls leak IN. `::` is not in IDENT either, so
      `Matrix::zeros(0, 0)` in host Rust counts as a Qu test of `zeros`.
      trailing_ident("Matrix::zeros") -> "zeros". Of the 57 `zeros(` in
      the walked corpus, some are exactly this shape.
  Net of (a) and (b): 64 of the 191 "Next" functions have test calls
  the counter cannot see. A third of the untested column is a
  tokenizer artifact, not a fact about the tree.

  Also: the walk misses 414 #[test] fns in qu-interp/src/*.rs other
  than lib.rs (plotting.rs 167, image.rs 61, table.rs 50). Most are
  Rust-level and would not add call sites, but "PLUS the #[cfg(test)]
  region of lib.rs" is not "plus the tests".

SEVERITY: misleading -- for the per-function rows, for the Alpha++
  rung, and for the RC-ready queue. Acceptable -- for the project
  version, which is the one number that survives every correction
  below (127+ functions stay at Next under any honest recount).

WHY:
  Your #2 is the worst of your five, and I can now put a number on it.
  The bench corpus is 36 .qu, 49 .py, 19 .m files, all scanned
  identically. 39 of the 156 Alpha++ functions have NO call in any .qu
  benchmark file: bwlabel, kmeans, pca, hilbert, stft, xcorr,
  periodogram, cond, softmax, train_test_split, regionprops ... Their
  Alpha++ was awarded because a MATLAB or NumPy reference script calls
  a function of the same name. `print` has 681 "bench" hits; that is
  Python's print(). The rung's text says "measured against MATLAB";
  what was measured is that MATLAB exists.
    probe: find benchmarks -name '*.qu' -exec cat {} + > b.txt; for nm in
    <aplus names>; do grep -qE "(^|[^A-Za-z0-9_.])$nm\(" b.txt || echo $nm; done

  The same defect drives the examples column. example_codes/ is 175 .m
  files and zero .qu; catalog/ is 99 .qu. So `abs` ex=1487 and
  `plot` ex=1001 are mostly MATLAB. ready_for() uses n_examples>0 as
  half of the RC gate.

  Your #3 is moot in a way you did not say: documented is 838 of 838.
  781 by call site in a stdlib chapter, 57 by backtick only. The column
  is a constant, so it carries no information, and the `d and ...`
  clause in ready_for() is always true. The Beta/RC queues are really
  "t>=2" and "t>=3 and (MATLAB mentions it or catalog calls it)".
    probe: grep -cE '^\| `[^`]+` \| `[^`]+` \| yes' All_functions_and_Features.md

  Your #4: 35 builtins are called in private/ (6 .qu, 2 .m), and none
  is DEFINED there (`function <name>(` finds nothing). The gate as
  written detects use, and use is not a leak. The leak vector this repo
  actually has is provenance: a method that lived in private/ and was
  ported into the engine (smoothmax appears in that list; the LSE crest
  factor is the known case). Names cannot see provenance. The gate
  should ask "does a builtin's source or chapter cite a private file",
  which is a different scrape, and I did not build it.

  Your #1, "a call site is not a test": you asked whether I have a fix.
  Partly. The test FUNCTION NAMES are a second corpus the tool ignores,
  and they encode subject: `zeros_still_builds_a_zero_vector_when...`
  is about zeros; `results = zeros(3)` before a parallel-for is not.
  For zeros the walked corpus has 57 call sites, 2 on an assert line,
  and 3 test fns naming it. Counting builtins that are a `_`-token of
  some #[test] fn name: 418 of 838 are the subject of at least one
  named test; 291 of today's 647 "tested" functions never are.
    probe: grep -A3 '#\[test\]' corpus | grep -oE 'fn [a-z0-9_]+' |
    tr '_' '\n' | sort -u | comm -12 names.txt -
  Cost: common words. all, any, set, get, first, last, plot, print,
  size, type, sort, close, write, filter, map all match test names
  about something else. It is better evidence than a call site, not
  clean evidence.

  Plain answer to your plain question: the per-function table is a
  REACHABILITY index -- "something in the tree mentions this name in
  call position" -- and it is a decent one once the tokenizer is
  fixed. It is not a maturity assessment, and the two places the tool
  goes beyond reachability (Alpha++, RC-ready) are where it is wrong.
  The project version is fine. The 838 rows should not be quoted.

PROPOSED CHANGE: Scan only Qu for evidence. In gen_version_ladder.qu,
  build the bench and examples corpora with a Qu-only extension list
  instead of CODE:
      QU_ONLY = (".qu",)
      bench_files   = walk("benchmarks", QU_ONLY)
      example_files = walk(...,          QU_ONLY)
  Two lines. Effects, measured: Alpha++ 156 -> 117; functions with any
  example evidence 304 -> 274; RC-ready 204 -> 190; `print` bench 681
  -> whatever the .qu files say. The rung text "measured against
  MATLAB" becomes at least "a Qu benchmark program calls it", which is
  still short of the claim but no longer answered by the other side of
  the comparison.
  (If you will take a second two-liner: add the backslash to the stop
  set so `\nplot` reads as `plot`. That alone rescues 28 Next rows and
  reintroduces nothing. Method syntax I would NOT fix by dropping `.`
  from IDENT -- that readmits every Rust .len()/.sum()/.min().)

WHAT IT WOULD COST: One tool run and 39 functions losing a rung they
  never earned, some of which Ahmed may have grown used to seeing at
  Alpha++. No new machinery, no new corpus, nothing to maintain. The
  tests corpus is untouched by this change, so #1 stays as it is.

WHAT IT STILL WOULD NOT CATCH: A .qu file under benchmarks/ that calls
  the function and never times it, never prints a number, and never
  runs the MATLAB side -- "on par with" is still unchecked. A test that
  calls the function as setup. A builtin whose implementation was
  ported from private/ but whose name does not appear there. Rust host
  calls with `::` still inflate test counts. And 414 tests in
  qu-interp/src/*.rs other than lib.rs remain unwalked.
