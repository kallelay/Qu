WHAT THIS IS

Qu tracks maturity per function on a seven-rung ladder. A generator
(tools/gen_version_ladder.qu) computes rungs up to 0.1.0-4.aplus from
evidence already in the tree -- tests, benchmarks, stdlib chapters,
example code. It deliberately CANNOT compute Beta or above, because
those rungs assert that something was tried with awkward inputs and
behaved, and scraping a repo never shows that.

That is the gap you are being asked to close.

WHAT YOUR REPLY IS AND IS NOT

Your results are EVIDENCE. They can move a function up to and including
0.1.0-4.aplus, and they populate the review queue.

Your results are NOT a signature. Beta (0.2.0-5.b), RC (0.3.0-6.rc) and
Public (0.4.0) are granted by Ahmed alone, by a row in
versions/ladder.tsv. This is not a slight to you -- it is the property
that keeps the ladder honest, because a rung that anything can grant is
a rung nothing checks. Report what happened; do not assign a rung.

If you find a defect, say what you ran and what came back. A finding I
cannot re-run is a finding I cannot record.

UNITS (class 5) -- answer to "survive, stripped, or fail?": ALL THREE,
depending on function and shape. Linear-family units (ohm/kohm/Mohm,
s/ms, Hz, V, A, F, H, W) are silently stripped to SI magnitude by most
elementwise and reduction builtins. That part is DOCUMENTED and
deliberate: docs/design/physical-units.md phase 2 (line 437) says
"as_num (and map1, the elementwise-math helper) unwrap a Family-tagged
quantity to its plain SI magnitude silently ... so sqrt(...)/etc. keep
working". The inconsistencies (undocumented):
  (a) abs(9 ohm) ERRORS ("cannot apply the operation to unit") while
      sin(9 ohm) => 0.412118, exp(1 ohm) => 2.718282, log(9 ohm) =>
      2.197225, sqrt(9 ohm) => 3 -- all other elementwise builtins
      silently unwrap the same scalar.
  (b) max(9 ohm) / min(9 ohm) / mean(9 ohm) / sum(9 ohm) ERROR ("expected
      a numeric vector, found unit") while the SAME function on a
      one-element unit vector or the two-argument form silently
      unwraps: max([9 ohm]) => 9, max(9 ohm, 10 ohm) => 10,
      min([9 ohm]) => 9, sum([9 ohm]) => 9.
  (c) abs errors on a scalar unit but strips on a unit vector:
      abs([1 ohm, -2.5 kohm]) => [1, 2500].
  No wrong NUMBER is produced (the strip is a consistent SI
  normalization), but the outcome for one and the same value depends on
  function, scalar-vs-vector, and arity in a way no doc states.
  Temperature stays loud, as designed: sqrt(9 degC) => "cannot apply a
  numeric operation to unit", abs(9 degC) => "cannot apply the
  operation to unit" (note the two different message strings for the
  same class), mean([10 degC, 20 degC]) => "expected a numeric vector;
  this list holds unit at position 0".
  Arithmetic between units works as designed: 1 ohm + 2 kohm =>
  2001 Ohm (tag kept); 1 ms + 2 s => 2.001 s; 5 V + 3 A => "operator
  `+` cannot combine a V quantity and a A quantity -- different
  physical-unit families don't add or subtract. See
  docs/design/physical-units.md §8."; 100 Hz * 0.01 s => "operator `*`
  cannot combine two unit-tracked quantities (Hz * s does not derive a
  new unit) -- cross-unit derivation isn't implemented. See
  docs/design/physical-units.md §3."

KEYWORD ARGS (class 8) -- the `dim=` in your example is not a wrong
kwarg: `dim=` is a language-level ALIAS of `axis=` (qu-interp/src/lib.rs
line 7901, eval_call_args), pre-extracted with `seed=` before kwarg
validation, so EVERY builtin accepts `dim=`/`axis=`/`seed=` and silently
ignores them when it doesn't use one: abs(5, dim=1) => 5, print(1,
dim=1) => 1, zeros(5, dim=2) => [0,0,0,0,0], all exit 0, no warning.
That softens the "unread kwarg is an error" guarantee for exactly these
three names. Genuine wrong kwargs are rejected with genuinely useful
messages:
  sqrt(16, wrong=1)  => "sqrt: unknown keyword argument `wrong=` -- sqrt
    takes no keyword arguments, and one it does not read would
    otherwise be silently ignored"
  print(1, 2, sep=", ") => prints "1 2" FIRST, then "print: unknown
    keyword argument `sep=` -- print takes no keyword arguments"
    (note: the output happens before the error)
  plot([1,2,3],[4,5,6], colr="red") => "plot: unknown keyword argument
